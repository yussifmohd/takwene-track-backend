# Takwene Track Management API Constitution

## Core Principles

### I. Clean Architecture & CQRS

- The solution MUST have four production projects with one-way dependencies:
  Domain ← Application ← Infrastructure ← Api. Domain has no package or project dependencies
  beyond the BCL (Ardalis.GuardClauses allowed).
- Application is organised by feature: `Features/<Feature>/Commands/<UseCase>/` and
  `Features/<Feature>/Queries/<UseCase>/`. Each use-case folder holds its request, handler,
  validator and (for queries) its DTO.
- Requests implement `ICommand<TResponse>` or `IQuery<TResponse>`; handlers implement
  `ICommandHandler<,>` or `IQueryHandler<,>`. Responses are always Ardalis `Result`/`Result<T>`.
- Commands change state through repositories, domain methods and the Unit of Work and return
  minimal data (an id or a bare Result). They MUST NOT return read models.
- Queries MUST NOT change state, MUST NOT use the Unit of Work, MUST read with no tracking via
  Ardalis Specifications and MUST project directly to DTOs. Entities never leave Application.
- Repositories MUST NOT save on their own. A single command-only pipeline behavior (selected by
  the command marker) commits the Unit of Work once per command.
- Business rules (e.g. track status transitions) live in Domain entities, not in handlers or endpoints.

Rationale: keeps write and read paths explicit, atomic and independently testable; mirrors the
reference project while fixing its lack of a Unit of Work.

### II. Result-Driven, Thin HTTP Edge

- Endpoints are Minimal APIs grouped with `MapGroup` (one endpoint-group class per feature). They
  only map request → command/query via `ISender`, and Result → HTTP via ONE shared mapping helper.
- Success responses return plain DTOs (never the Result wrapper). Every error response is
  RFC 7807 ProblemDetails (validation errors as `errors` dictionary), including unhandled
  exceptions via a global exception handler. No stack traces or internal details leak.
- Expected failures (not found, validation, conflicts, invalid transitions) are Results, not exceptions.
- Routes live under `/api/...`; `/health` is anonymous. The OpenAPI document is generated by the
  built-in .NET OpenAPI support and is the contract consumed by the frontend repo.

### III. Tests Ship With Features (NON-NEGOTIABLE)

- Every phase delivers unit tests in the same branch as the code: command handlers, query
  handlers, validators, specifications, domain rules, pipeline behaviors and Result→HTTP mapping.
- Test folders mirror production (`Application/<Feature>/Commands|Queries`, `Domain`, `Api`).
- Stack: xUnit, NSubstitute, Shouldly. FluentAssertions is forbidden.
- A phase is not done unless `dotnet build` is warning-clean for new code and `dotnet test` is green
  locally and in CI.

### IV. Security by Default

- All write endpoints require the Admin role via an authorization policy; reads are public.
- JWT validation MUST check issuer, audience, lifetime, signing key and algorithm. Signing keys,
  connection strings and admin credentials come from configuration/environment only; nothing
  secret is committed (`.env.example` holds placeholders).
- Passwords are hashed by ASP.NET Core Identity; login failures return one generic message
  (no user enumeration) and use lockout.
- Input is validated (FluentValidation) with explicit length limits; request DTOs never bind
  directly onto entities (no over-posting). No raw SQL string concatenation.
- CORS uses an explicit allow-list. Containers run as non-root. Security findings are logged in
  `docs/ai-log.md` and summarised in `DECISIONS.md`.

### V. Spec-Driven, Traceable Delivery

- Every phase follows Spec Kit: specify (WHAT/WHY, no stack) → clarify → plan (HOW, with an
  exported OpenAPI contract in `specs/<feature>/contracts/`) → tasks → analyze → implement.
  No production code before spec, plan and tasks exist.
- One branch per phase from an up-to-date main, Conventional Commits, small commits, no commits
  to main, no squash, no force-push. Each phase ends with a PR; a human merges.
- AI usage is logged honestly per phase in `docs/ai-log.md` (generated vs written, security
  issues, mistakes and fixes).

### VI. Simplicity & License Hygiene

- Build only what the current phase needs; no speculative abstractions, no extra services.
- Every NuGet package's license is checked before it is added. Commercial or source-available
  packages are forbidden (e.g. MediatR ≥ 13, AutoMapper ≥ 15, MassTransit ≥ 9,
  FluentAssertions ≥ 8). MediatR is pinned to exactly 12.5.0.
- Versions are pinned (no floating ranges, no "latest"); pinned versions are recorded in Memory.md.

## Technology Stack & Constraints

- .NET 10 (SDK pinned in `global.json`, rollForward latestFeature), C# with nullable enabled.
- Minimal APIs, MediatR 12.5.0, FluentValidation, Ardalis.Result, Ardalis.Specification (+ EF Core),
  Ardalis.GuardClauses.
- EF Core 10 + Npgsql (PostgreSQL 17) with snake_case naming; migrations in Infrastructure;
  `dotnet-ef` 10.x via local tool manifest (`.config/dotnet-tools.json`).
- ASP.NET Core Identity + JWT bearer (HS256, 60-minute access tokens, no refresh tokens).
- Built-in OpenAPI (`AddOpenApi`/`MapOpenApi`) + Scalar.AspNetCore with a Bearer security scheme
  via a document transformer; docs exposed only in Development. Swashbuckle/Swagger UI forbidden.
- Serilog console logging; ProblemDetails + global exception handler; `/health` endpoint.
- Docker: multi-stage, non-root, healthcheck; own `docker-compose.yml` (db + api) on the external
  network `trackmgmt-net`; migrations + seed on startup controlled by a configuration flag.
- CI: `.github/workflows/backend-tests.yml` on pull_request to main (restore, build, test, TRX +
  coverage artifacts).

## Development Workflow & Quality Gates

Definition of Done per phase: builds clean; migrations included when the model changes; tests
written and passing; CI green; `docker compose up` still works; spec, plan and tasks committed;
Memory.md and `docs/ai-log.md` updated; PR opened with summary, test evidence and checklist.
The backend PR of a phase is merged before the frontend PR.

## Governance

This constitution supersedes other practices in this repo. Amendments require the user's
approval, a version bump (MAJOR: principle removed/redefined; MINOR: principle or section added
or materially expanded; PATCH: wording) and an updated Sync Impact Report. Every plan's
Constitution Check and every PR review verify compliance; any violation must be justified in the
plan's Complexity Tracking table. Runtime guidance: `CLAUDE.md` and `Memory.md`.
